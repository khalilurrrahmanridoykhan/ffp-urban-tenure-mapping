# Dashboard

A static web app (plain HTML/CSS/JS, [Leaflet](https://leafletjs.com/)
via CDN, no build step, no backend): an interactive tenure-security
choropleth over the settlement, a working adjudication-queue worklist
(filterable by category/severity, click a finding to fly to and
highlight the parcel(s) it's about), and a per-parcel detail panel
(claimant, tenure type, dispute status, evidence) pulled straight from
the STDM tables.

## Why Leaflet `CRS.Simple`, not a real basemap

The imagery is real, but its published coordinates are deliberately
stripped to an arbitrary local grid (see `data/synthetic/README.md`) —
so a real-world slippy-map basemap would either not line up with
anything, or defeat the point of stripping the coordinates in the first
place. Leaflet's `CRS.Simple` mode is built for exactly this case (floor
plans, game maps, anything non-geographic): the real imagery is loaded
as a plain image overlay, and the parcel polygons are pre-converted from
local metres to that image's pixel space by
`scripts/export_webapp_data.py` — the page itself does no
coordinate-system reasoning at all, just plots what it's given. The
map's attribution (bottom-right corner) credits the real imagery/building
sources, same as any map using real data should.

## Data

Everything under `data/` is a static export, regenerated by
`scripts/export_webapp_data.py`:

- `imagery.jpg` — the settlement imagery, JPEG-compressed for the web
- `tenure_security.geojson` — every parcel with its security
  classification and claimant/tenure details (joined in from `stdm.gpkg`
  at export time, since there's no live database to query from the page)
- `adjudication_queue.json` — the Phase 5 findings
- `meta.json` — image dimensions, so the page knows the map bounds

No live field-data ingestion, no writes — this is a read-only snapshot,
regenerated whenever the upstream data changes.

## Deployment

Published via **GitHub Pages**, using the Actions-based deploy in
`.github/workflows/deploy-pages.yml` (triggers on any push to `webapp/`
on `main`) — not Vercel: this dashboard has no server-side needs, so
keeping it entirely on GitHub (code, data, and the live demo all in one
place, no separate hosting account) is the better fit here than it was
for the live-API Prohori dashboard.

Reproduce locally: `python3 scripts/export_webapp_data.py`, then serve
the `webapp/` folder with any static file server (e.g.
`python3 -m http.server` from inside it) — opening `index.html` directly
via `file://` won't work, browsers block `fetch()` of local files under
that scheme.
